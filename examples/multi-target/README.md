# One setup, several targets

This example uses the unreleased checkout CLI and runtime. Its local `moon.work`
selects the repository source even though `moon.mod` retains the registry version.
Use moon/moonrun 0.1.20261012, moonc/core 0.10.15+943464bfa and async 0.22.4,
the same toolchain as the compatibility tests. No supporting registry CLI is
assumed or fetched.

From the repository root:

```sh
mise run examples:multi-target
mise run examples:multi-target -- wasm-gc
```

The task builds the local CLI once. The stdlib Python verifier consumes that
binary, copies the example into a temporary workspace and runs actual tests.
The full run checks ten selections, 23 passing tests and 23 scenarios, including
both modes together on native and a feature edit regenerated by Moon. It also
compares committed generation byte for byte and proves unchanged manual
generation preserves bytes and modification times. Logs and counts are in
`_build/examples-multi-target/` at the repository root.

`src/definitions/world.mbt` defines the World, three steps, two hooks and fresh
options exactly once. The public World has a private counter. Each options call
creates a new stateful Messages formatter; the factory stores no global options
or sink. Both scenarios assert that the counter starts at zero.

`moonspec.json5` selects async by default and explicitly selects sync on Wasm-GC.
The generator embeds the complete feature in a common portable package. Its
thin launchers declare these targets:

| Generated package | Targets |
|---|---|
| `src/suite/moonspec_gen/shared` | `wasm`, `wasm-gc`, `js`, `native` |
| `src/suite/moonspec_gen/sync` | `wasm-gc` |
| `src/suite/moonspec_gen/async` | `wasm`, `js`, `native` |

To regenerate and test the working example directly:

```sh
mise run build:cli
export PATH="$PWD/_build/bin:$PATH"
cd examples/multi-target
moonspec gen tests features/counter.feature -o src/suite
moonspec gen build features/counter.feature --package src/suite --apply
moon test src/suite/moonspec_gen/sync --target wasm-gc
moon test src/suite/moonspec_gen/async --target wasm
moon test src/suite/moonspec_gen/async --target js
moon test src/suite/moonspec_gen/async --target native
```

Keep that local `moonspec` on `PATH`: generated per-package rules invoke it
through Moon. Do not pass `--moonx`; shared-policy registry capability has not
been verified and the generator rejects it before writing.

The verifier also generates a second suite with the scalar CLI override:

```sh
moonspec gen build features/counter.feature --package src/sync_suite \
  --execution sync --apply
moon test src/suite/moonspec_gen/async src/sync_suite/moonspec_gen/sync --target native
```

That override replaces the execution object, inherits the same shared factories,
and emits sync launchers for all four targets. Both native suites run together
with one definition package and one config. The extra suite is temporary in the
verifier; only `src/suite/moonspec_gen` is committed here.

Edit feature bodies or existing grouping settings and Moon regenerates the
affected test sources. Rerun `gen build --apply` for target sets, packages,
feature lists, test kinds, or adding/removing config paths. The generator owns
the manifest and files under `moonspec_gen`, rejects modified files and
collisions, and removes only unchanged stale outputs it previously recorded.

The shared options remain sequential. Enabling `parallel(true)` would make a
sync run raise `SyncExecutionError::ParallelNotSupported` before World factories,
hooks or events. Use a
separate explicit async suite/factory for parallel settings. Wasm-GC launchers
do not import the async runtime. All targets still need the standard MoonBit
host ABI; embedded source avoids feature reads, and file/stderr destinations
still require host I/O. There is no browser filesystem emulation.

See the [target-policy guide](../../docs/guide/testing-strategies.md#one-setup-across-targets) for config
precedence, package visibility, safe regeneration and source API migration.
